## 2. Token discipline -- ACTIVE FROM YOUR VERY FIRST TOOL CALL

Context is re-sent every turn, so cost ~= bytes_printed x turns_remaining.
A dump on turn 3 of a 40-turn session is paid ~37 more times, and there is no
way to un-print it. Be strictest at the START, when you are exploring and
output size is least predictable.

These rules apply even before you have finished reading the skills above:

  a. Cap WIDTH, not just line count. `tail -30` bounds lines and says nothing
     about bytes -- one config/argparse/JSON line can be 17,000 chars (~4k
     tokens) on its own. Always compose both:
         tail -n 30 x.log | cut -c1-200

  b. Unconditional byte cap on anything you have not run before this session:
         <command> 2>&1 | head -c 2000

  c. Count before you list. Ask for the answer, not the data:
         find ... | wc -l        rg -c pattern file        test -f x && echo yes
     Only list once the count says listing is safe (< ~30 short entries).

  d. Never search from /. Scope it, depth-limit it, prune generated trees
     (build/, jit/, .git/, 3rdparty/, __pycache__/, node_modules/):
         find <scoped-dir> -maxdepth 4 -name 'pat' -not -path '*/build/*' | head -20
     Prefer `rg --files -g 'pat'` inside a repo.

  e. Bounded git only. `git diff --stat -- <path>` first, then one file.
     Never bare `git diff` / `git log` / `git show`.

  f. Long jobs: full log to a FILE, only markers to the chat. The filter must
     be INSIDE the command -- output of a background task cannot be filtered
     after the fact:
         <job> > /tmp/job.log 2>&1
         echo "exit=$?"; rg 'PASS|FAIL|Error|Traceback' /tmp/job.log | tail -20 | cut -c1-200

  g. ONE channel per log. Do not run a monitor AND poll the same file -- you
     pay for identical lines twice for zero extra information.

  h. Parse structured responses, never dump them. Extract the fields:
         curl -s "$URL" | python3 -c "import json,sys; d=json.load(sys.stdin); print(d['x'])"

  i. Do NOT re-read a file you just edited to verify it. A failed edit raises
     an error; silence means success. Same for re-ls / re-running "to be sure".

  j. Edit in place (Edit / sed -i / small python script). Never rewrite a whole
     large file to change a few lines.

Escalation ladder -- go down a step only if the step above genuinely did not
answer the question. Most exploration should stop at 2 or 3.
     1. wc -l / wc -c / rg -c        -- how much is there?
     2. rg -o '<narrow pattern>'     -- just the value I need
     3. rg '<pat>' | head -20 | cut -c1-200
     4. sed -n 'A,Bp' file           -- one targeted range
     5. read the whole file          -- rare, small files only

## 3. Durable state lives on disk, not in this chat

    The doc is the source of truth; the chat is scratch.

## 4. Environment -- detect, do not assume

Do not assume CUDA/NVIDIA. Detect first, cheaply, in one batched message:
  - GPU vendor/arch, driver tool (rocm-smi vs nvidia-smi)
  - whether this is a git repo, and its dirty state (--short | head)
  - which of rg / jq / fd are available
Then state what you found in one or two lines and proceed.

## 5. How I want you to work

  - Batch independent tool calls into ONE message. Do not serialise reads,
    greps and checks across many turns.
  - Decide and act. Ask me only when genuinely blocked or when two readings of
    my request would produce materially different work.
  - Report faithfully: if something failed, show the actual error; if you
    skipped part of the task, say which part and why.
  - Do not commit, push, or touch anything outside the working directory

Acknowledge with a SHORT confirmation (a few lines, not a summary of the
