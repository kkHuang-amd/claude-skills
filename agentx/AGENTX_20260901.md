## FP4 indexer (#37353) — integration plan (survey resolved 2026-09-01)

### Q1 — TBO: supported. The "not supported" note is stale.

Only the PR's *first* commit message (`a627e90`) says "MTP, TBO, HiCache and PD
disaggregation are not supported yet". In the final tree TBO is handled
explicitly, in exactly one place — `_refresh_fp4_prefill_workspace()` in
`deepseek_v4_backend_hip_radix.py`, added by `37b73f5d04` (the MTP commit, i.e.
*later* than that note):

```python
if (
    get_parallel().attn_cp_size != 1
    or getattr(forward_batch, "tbo_children", None)
    or getattr(forward_batch, "tbo_parent_token_range", None) is not None
):
    return
```

That skip is **not** a disable of the feature. `prepare_fp4_prefill_workspace()`
only pre-computes `cta_info` via aiter's `compute_prefill_schedule` outside
graph capture; its `row_to_batch` / `local_starts` are the same `arange` /
`zeros` that the no-workspace path builds inline, and
`aiter_fp4_paged_mqa_logits()` handles `workspace is None` by passing
`pinned = {}` and letting the kernel compute its own schedule. So under TBO the
FP4 prefill kernel still runs — it only loses the pinned schedule, which exists
for CUDA-graph safety, and DSV4 TBO is eager-prefill-only anyway
(`tbo_supports_cuda_graph = False`, already present at our HEAD).

Decode is unaffected: DSV4 decode / target-verify graphs are non-TBO, so the
pinned decode workspace is still used there.

No other TBO gate exists — those two lines are the *only* `tbo` /
`two_batch_overlap` additions in the entire PR diff. All FP4 state
(`fp4_decode_workspace`, `fp4_prefill_workspace`, `fp4_k_write_metadata`) lives
on the per-backend `DSV4Metadata`, so TBO's per-ubatch child backends each own
theirs; there is no module-level cache for the two ubatches to race on.

**Consequence for the benchmark:** c128 DP+TBO is a valid target, no
substitution needed. The honest caveat is that TBO gives up the prefill
workspace, so on this prefill-heavy trace the gain may read *smaller* than the
PR's +5.8 % at conc 48 (measured without TBO). If the TBO pair reads flat, a
non-TBO c128 pair is the follow-up that separates "FP4 does nothing here" from
"TBO ate the prefill-side win".

## Carried forward from the old node (methodology only, no numbers)

These cost real time to learn and still apply here:

- **`GPU pool` / `kv.gpu_usage_pct` is a max-of-max**, one sample out of
  ~29,000, not an occupancy level. Use mean occupancy or the fraction of
  seconds above 0.7, recomputed from `server_metrics_export.json`.
- **Exit codes:** `124` = driver timeout (hang *or* a healthy arm on too tight
  a cap), `137` = deliberate operator SIGKILL, `1` = aiperf refused to certify
  (coverage < 95 %, server was fine).
- **Never edit a launcher while an arm is running** — bash reads scripts lazily
  by byte offset and the running shell will execute garbage.
- **A dead server keeps answering HTTP 200** and aiperf then waits forever.
- The launcher's **GPU drain gate** polls up to 15 min for every GPU ≤ 10 %
  VRAM; a half-drained node fails RCCL init with a misleading HIP error.
- Analysis tools ship with this skill: `arm_report.py <arm> [<baseline>]`
  (prints sanity gates before the headline) and `warmup_check.sh <arm>`.
