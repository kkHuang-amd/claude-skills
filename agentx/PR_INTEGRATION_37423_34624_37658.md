## Why #34624's fusion blocks FP4, and what it would take to lift it

**Not a chronology artifact.** `enable_deepseek_v4_fp4_indexer` landed **2026-06-02**
(#26209), two months *before* #34624's first commit (**2026-08-12**, `8d5dc6626f`), and
`and not use_fp4_indexer` was in that very first commit. The author excluded FP4 deliberately.
What *is* newer is the ROCm FP4 *store*: `aiter_k_indexer_fp4_cache_write` arrived
**2026-09-02** via #37353 "[AMD] Enable FP4 indexer for Deepseek V4" — that is the path our
arms take.

**The real blocker is that FP4's second kernel belongs to aiter.** Both paths are two
launches, but not the same two:

- non-FP4: `compress_forward` (JIT cuh) then `compress_norm_rope_store` → `module.forward`
  (JIT cuh). #34624 fuses these two JIT kernels into one.
- FP4 on HIP: `compress_forward` (JIT cuh, writing a bf16 temp `compress_out`, a per-call
  `new_empty`) then **`aiter.rmsnorm_rope_rotate_activation_fp4quant_kvcache`**, which does
  rmsnorm + rope + rotate + fp4 quant + paged write in one aiter kernel, into a separate
  `k_scale` tensor, addressed through a `write_metadata` `(positions, slots)` indirection.

`fused_compress4_norm_rope_hip.cuh` contains **zero** occurrences of `fp4`. Its indexer
epilogue quantises to **fp8 e4m3** with an fp32 scale appended *inside the same page*
(`scale_ptr = page_ptr + (128 << kPageBits) + offset * 4`), plus an optional preshuffle
tiling. Dropping the guard would make it write the wrong layout silently.

**The fusion opportunity is real, though:** under FP4 the bf16 `compress_out` temp is
allocated and round-tripped through HBM every layer of every step, which is exactly the cost
#34624 exists to remove.

Two ways to get it, and the second is the right one:

1. **Add an fp4 epilogue to the JIT kernel.** Structurally close — the existing indexer
   epilogue already does per-row dynamic quant, paged addressing and a preshuffle layout —
   but it must reproduce aiter's e2m1 packing, e8m0 scale tensor and `write_metadata`
   addressing exactly, and it duplicates a kernel AMD maintains. Note the precedent: in
   #37423 a silently permuted weight passed every shape/dtype/stride check and gave
   **GSM8K 0**. Same hazard class.
2. **Push the fusion into aiter**, i.e. a variant of
   `rmsnorm_rope_rotate_activation_fp4quant_kvcache` that takes `kv_score_buffer` /
   `kv_score_input` and does the compress itself. This is architecturally where the second
   kernel already lives, and it is exactly the shape of #37658 (which fused inverse-RoPE into
   the `wo_a` quant by using an aiter op).

**Before either:** #34624's measured +2.95 % was on the non-FP4 path and is **inside our
5.67 % replicate spread**. Profile what the `compress_forward` launch plus the `compress_out`
round-trip actually costs per decode step on an FP4 arm before spending kernel work on it.

## Prerequisites present on this node

`aiter c16d44b93` has both required ops: `batched_gemm_a8w8_mxscale`
(`aiter/ops/batched_gemm_op_a8w8.py`) and `inverse_rope_group_quant`
(`aiter/ops/inverse_rope_group_quant.py`). Both PRs gate on gfx950; we are gfx950.

## Why this is worth an arm despite TTFT being the open axis

All three are **decode-path** wins, and decode margin is exactly what our TTFT problem
needs. We already beat ATOM on ITL (91.11 vs 97.6 ms at c256) and lose only on TTFT, which
is policy-imposed deferral controlled by `--prefill-decode-interval`. A cheaper decode step
buys more ITL margin, which can then be **spent** on TTFT by lowering the interval — the
same trade the whole investigation turns on. Published claims, on other images and shapes:

- #37658 stack: median TPOT 88.95 (bf16) → 82.45 (#37423) → 76.20 ms, i.e. −14.3 % vs bf16,
  at 128k/1k conc 64 DP8/TP8 MTP.
- #34624: +2.95 % tok/s at conc 64 TP8+DP8, A-B-B-A averaged.
- #37423 on AgentX itself: 20,143 → 20,685 tok/s at conc 64, +2.7 %.

## Caveats before quoting any of this

- Every number above is from **other images** (`rocm/mlperf-inference:v0.5.18-rocm720`,
  `rocm/sgl-dev:v0.5.17`) and other shapes; none is an AgentX c128/c256 arm on our tree.
- **Replicate spread here is 5.67 % on throughput.** +2.7 % and +2.95 % are *inside* it.
  Only the #37658 TPOT claim (−14.3 %) is large enough to survive our noise band, and TPOT
  is not throughput.
- #37658's gate is **default off**; #34624's three gates default **on** upstream, and the
  local rework leaves `SGLANG_OPT_NATIVE_BPRESHUFFLE_SCALE` default 0. State which gates an
  arm actually had.
- Accuracy: #37423 GSM8K 0.9689 (vs 0.9674 bf16), #37658 0.947, #34624 94.5–94.8 % against
  a 94.7 % baseline. All null-shaped, none run on our tree/image.
- #34624 adds a JIT `.cuh`, so the first arm pays a kernel build; #37423/#37658 are Python
  plus aiter ops already present.
- #37423 CI is red (Base 🚫, Extra ❌, ROCm ❌) as of Sep 4.

## #37580 — added, and it composes with our chunking rather than just coexisting

Merged **clean** into the combined branch; it touches one file
(`kernels/jit/csrc/deepseek_v4/topk_v2.cuh`) that none of the other three go near. The
change is an `#ifdef USE_ROCM` early return inside `TopKKernel::plan`, so non-ROCm builds
are byte-identical in behaviour.

It matters more here than its 1.5 us headline suggests. Upstream's `run_topk_transform`
rebuilds a per-chunk plan (`plan_topk_v2(c4_seq_lens[rows])`) for every row chunk on HIP,
and both our fp4 and fp8 row-chunking paths multiply the number of those calls. #37580 makes
each one skip its launch on our platform.

**Residual cost, stated honestly:** `plan_topk_v2` still allocates
`seq_lens.new_empty(bs + 1, _PLAN_METADATA_INTS)` and still crosses into pybind — only the
kernel launch goes away. So per chunk this saves ~1.2–1.5 us, not the whole call.

**Correctness rests on a claim we have not verified ourselves:** the plan metadata is read
only by the cluster path (`topk_persistent_cluster_kernel`, `topk_main_kernel<kLevel=3>`),
which ROCm compiles out, so leaving the buffer uninitialised is safe. That is the reviewers'
reasoning plus `test_topk_v2.py` 278 passed on MI355X, not a measurement of ours.
