## PR #37591 (ROCm exact DSA top-k) — assessed 2026-09-16, no action needed

Already in our tree (squash `6cee9285a3`, files byte-identical to the PR head) and
compiled into the installed `sgl_kernel` .so (`coop_topk_kernel` symbols present).
It is **dormant on the DSV4 path** and cannot be adopted as-is:

1. `dsv4/indexer.py` never calls `fast_topk*` — it dispatches to `topk_transform_paged_v2`
   (JIT `deepseek_v4/topk_v2.cuh`, `SGLANG_OPT_USE_TOPK_V2` defaults True) or the AOT
   `deepseek_v4_topk` fallback. No flag routes it to the PR kernel.
2. `fast_topk_transform_fused` needs the `page_size=1` wide page table that DSV4's fused
   decode graph deliberately drops (`dsa_drop_wide_page_table`), and returns only one of
   the two outputs DSV4 sometimes needs (transformed + raw indices).
3. The op is instantiated for a compile-time `kTopK=2048` (DSv3.2); DeepSeek-V4-Pro uses
   `index_topk=1024`, which trips both the python assert and a `TORCH_CHECK`.

Measured on this node (scripts `/tmp/topk_recall.py`, `/tmp/topk_recall_real.py`,
`/tmp/threshold_bin.py`; captures in `/shared_nfs/kk/indexer_scores`, 8 batches x 64 rows
from a 42k-token prompt, dumped via a temporary env-gated hook in `run_topk_transform`
that has since been reverted):

- Synthetic, topk=2048, seq 32k: recall v2 vs coop = 1.0/1.0 diffuse, 0.0001/1.0 tiny,
  0.026/1.0 clustered. Timing: v2 is faster where it is exact (15 vs 24 us), slower where
  it is not. The PR's claim reproduces exactly.
- **Real DSV4 indexer scores: recall 1.0000 on every row.** The failure mode needs > 2048
  entries in the fp16 bin holding the k-th value; our worst captured row puts 19 entries
  there (0.9 % of the row), so the cap would only be reached at ~222,000 scored positions.
  The c4 compressed window is ~2,064 wide at a 42k-token context (~20x compression), so
  production is three orders of magnitude away from the cliff.

- Reproduced the PR's own sweep config (width 131,072, live 100,500, topk 2048, MI355X):
  coop wins below batch 32 (24.3 vs 29.1 us at batch 1) and loses above it (52.8 vs 40.1
  at batch 256), matching the PR. The deciding variable is **row width**, not the GPU:
  coop's row-split only pays off when one row is wide enough to leave the GPU idle at low
  batch. At 4k/8k/32k widths v2 wins at every batch from 1 to 224.

Conclusion: no accuracy exposure and no speed win available, so porting the coop
fp32-refine / overflow-rescan into `topk_v2.cuh` is not worth doing now. Re-check if a
model ships a much more concentrated indexer score distribution or a far wider c4 window.
