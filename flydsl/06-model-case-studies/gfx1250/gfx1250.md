# gfx950 cross-validation of the gfx1250 recipe (2026-07-07)

Purpose: confirm that the SGLang integration changes made for gfx1250 (the
self-contained **Triton `fused_qk_rmsnorm`** and the **linear bf16-dequant**)
do NOT themselves cost accuracy, by running the *same* code path on **gfx950**
hardware — where the real MXFP4 kernels work — and checking GSM8K against the
gfx950 reference of 0.93-0.94. If gfx950 reproduces the reference, the ~11%
gfx1250 gap is isolated to the one unavoidable divergence: the a8w4 MoE kernel.

## Setup

- HW: 8x **MI355X gfx950**, 309 GB VRAM each. **TP2** (single card can't hold the
  ~353 GB bf16-dequant model).
- sglang: modified tree at `/sgl-workspace/sglang_gfx-1250` (rev `7aa6082`), forced
  onto `sys.path` via `PYTHONPATH` (the pip-editable install still points at the old
  `/sgl-workspace/sglang`).
- aiter: stock gfx950 build at `/sgl-workspace/aiter` (unmodified — the gfx1250
  flydsl fixes are arch-gated and not needed here).
- Model: `/shared_nfs/huggingface_models/amd/DeepSeek-R1-0528-MXFP4` (Quark W4A4, fp4/fp4 confirmed).
- Launch script: `sglang_gfx-1250/run_ds-r1_gfx950.sh` (copy of the gfx1250 script
  with `--tensor-parallel-size 2`, `HIP_VISIBLE_DEVICES=0,1`, model path fixed to
  `/shared_nfs/huggingface_models/...`; all workaround env kept, incl. `AITER_FORCE_A8W4=1`,
  `ENABLE_CK=0`, `SGLANG_USE_ROCM700A=1`, `--kv-cache-dtype auto`, cuda graph ON).

## Which kernels actually ran on gfx950 (verified from server logs)

`AITER_FORCE_A8W4=1` drives three things; two are env-gated (fire on any arch),
one is arch-gated to gfx1250:

| component     | gfx950 behavior                                             | vs gfx1250 |
|---------------|------------------------------------------------------------|------------|
| qk-rmsnorm    | **Triton** `fused_qk_rmsnorm` (env-gated, not arch-gated)   | same       |
| linear        | **bf16-dequant** + `F.linear` (env-gated, not arch-gated)   | same       |
| MoE           | **native a4w4** — log shows `float4_e2m1fn_x2 x float4_e2m1fn_x2, per_1x32` (aiter a8w4 branch is `if get_gfx()=="gfx1250"`, so it's a no-op here) | **differs** (gfx1250 forced a8w4) |

So the MoE gemm is the *only* forced divergence between the two platforms; the
qk-rmsnorm and linear paths are byte-for-byte the same code.

Sanity: decode coherent (`"...Paris. Paris is known as the city of love..."`),
not the token-0 degeneration; CUDA-graph capture succeeded; invalid rate 0.000.

## Results — GSM8K (5-shot, greedy, completion)

| run                          | Q    | Accuracy | Invalid | tok/s | latency |
|------------------------------|------|----------|---------|-------|---------|
| gfx950 TP2 (this experiment) | 200  | 0.945    | 0.000   | 489   | 40 s    |
| gfx950 TP2 (this experiment) | 1319 | **0.932**| 0.000   | 668   | 202 s   |
| gfx950 reference (expected)  | -    | 0.93-0.94| -       | -     | -       |
| gfx1250 a8w4 (EXPERIMENT_LOG E15) | 1319 | 0.822 | 0.000 | 158 | 914 s |

## Conclusion

- gfx950 with the **exact same SGLang changes** (Triton qk-rmsnorm + linear
  bf16-dequant) reproduces the reference: **1319-question GSM8K = 0.932**
  (200 Q = 0.945), invalid 0.000.
- => The **Triton `fused_qk_rmsnorm` is accuracy-neutral** and the serving
  integration is correct. Neither is the source of the gfx1250 shortfall.
- => The gfx1250 gap (0.932 gfx950 a4w4 -> 0.822 gfx1250 a8w4, ~11%) is cleanly
  attributable to the **a8w4 grouped MoE kernel numerics** — the single component
  forced to differ because gfx1250 lacks the fp4-activation scaled-WMMA. This
  matches the EXPERIMENT_LOG E16 hypothesis (token/max_m-dependent logits_diff
  growth in the FlyDSL grouped a8w4 kernel).
- Next optimization work should target that FlyDSL grouped a8w4 MoE kernel, not
  the norm / linear / serving layers.

Note: under cuda-graph (used here) decode replays the capture-mode alt-stream
torch `q_a/kv_a` layernorm branch, so the Triton qk-rmsnorm kernel is exercised
in eager only; both are numerically equivalent (see EXPERIMENT_LOG E15).

# E26 follow-up (2026-07-09): gfx950 absorb-BMM ablation — absorb is NOT the gap

Second gfx950 experiment, testing the E25 "quantization-matching" thesis for the MLA
absorb BMM (gfx950 runs it fp4 via `quark_post_load_weights`; gfx1250 runs it bf16).
Single-node A/B, no cross-node confound, both TP2 in parallel, same modified tree
(`/sgl-workspace/sglang_gfx-1250`), model `/shared_nfs/huggingface_models/amd/DeepSeek-R1-0528-MXFP4`.
Pure runtime monkeypatch (`scripts/gfx950_disable_absorb_fp4_sitecustomize.py`,
`SGLANG_DISABLE_QUARK_ABSORB_FP4=1`) — **no source edits**; hook confirmed firing on
every TP rank (`[gfx950_abl] quark_post_load_weights -> bf16 absorb`).

| absorb path (MoE stays a4w4) | 200Q  | 1319Q  | Invalid |
|------------------------------|-------|--------|---------|
| fp4 (gfx950 native)          | 0.950 | 0.944  | 0.000   |
| bf16 (mimic gfx1250)         | 0.950 | 0.942  | 0.000   |

**0.944 vs 0.942 (1319) = ~2-3 questions = noise.** Forcing the absorb to gfx1250's
more-precise bf16 does NOT drop accuracy toward 0.85. => **absorb-BMM precision is not
the gfx1250 gap** (E25 quant-matching thesis is false for this path). Remaining suspect =
a8w4-vs-a4w4 MoE scheme interaction and/or a cross-layer effect visible only via the
cross-node per-layer dump (`HANDOVER_crossnode_dump.md`), which is now the primary next
localizer. See EXPERIMENT_LOG E26 and STATUS.md.
