# Triton 3.6 versus 3.7 C32 trace investigation — 2026-08-13

## Question

Does the C32 endpoint regression with Triton 3.7 appear primarily inside
Triton-generated GPU kernels?

## Controlled evidence

The endpoint A/B changed only Triton and its matching `triton-kernels` package:

```text
Triton 3.6 C32: 6176.87 tok/s
Triton 3.7 C32: 5881.93 tok/s
delta:             -5.00%
```

Returning to Triton 3.6 also restored C8 and C16 by 1.69% and 2.98%. This
identifies the Triton runtime/codegen stack as the causal high-concurrency
variable more strongly than an observational trace alone would.

## Trace attempts

Two matched PyTorch/ROCtracer pairs were captured:

```text
short decode: 512 input / 128 output / C32
endpoint:     8192 input / 1024 output / C32
window:       15 seconds after server-confirmed C32 decode
rank:         TP0 analyzed
```

The endpoint server was active throughout the window:

```text
Triton 3.6 observed generation throughput: about 1019-1023 tok/s
Triton 3.7 observed generation throughput: about 1021-1024 tok/s
```

However, PyTorch's ROCm profiler recorded only one expanded CUDA Graph replay
per 15-second window:

```text
Triton 3.6: 6544 kernel events; 54.08 ms kernel busy; 99.64% apparent idle
Triton 3.7: 6553 kernel events; 52.54 ms kernel busy; 99.65% apparent idle
```

The server log confirms hundreds of decode steps during those same windows.
The apparent idle time is therefore a profiler visibility artifact: HIP CUDA
Graph replays were not expanded into their internal kernel events.

The visible single-replay Triton kernels did not show a regression:

```text
SGLang attention residual _agg_kernel:
  p50 8.74 us -> 8.10 us

AITER Triton GEMM _gemm_a16_w16_kernel:
  no material total-duration delta

AITER Triton MLA merge _fwd_kernel_stage2_asm:
  no material total-duration delta
```

An external `rocprofv3` attach successfully injected into TP0 but produced no
kernel CSV on detach. Launching the full server under `rocprofv3` increased
startup beyond 12 minutes, disrupted the workload during the collection
period, and terminated the server without a usable production-path trace.
Those runs are rejected as methodologically invalid.

## Conclusion

The 5% endpoint gap is causally attributable to the Triton 3.7
runtime/codegen package, but the available profiler data does **not** localize
it to a specific Triton kernel.

In particular, the valid visible replay does not support the claim that one
Triton kernel became slower. Remaining credible mechanisms include:

```text
different generated code inside graph replays not exposed by ROCTracer
HIP graph launch/runtime interaction
context- or later-wave-dependent behavior absent from the first visible replay
CPU/runtime scheduling changes associated with Triton 3.7
```

Do not disable CUDA Graph solely to obtain a trace and then treat that trace as
production attribution; doing so changes the execution path under
investigation.

## Combined-trace coverage proof

The older global-profiler method captured prefill and decode in one trace with
PyTorch API records. CPU `aiter::fused_moe_` counts match exactly at 1564 for
both runtimes, but Triton 3.7 loses more than 99% of graph-replay GPU events:

```text
kernel                         Triton 3.6   Triton 3.7
MoE stage1                          11868            92
_agg_kernel                         27156           186
fused KDA                            8901             0
MLA merge                            3096             0
cross-device reduce                 23936           187
```

This confirms a Triton-3.7-specific ROCTracer visibility failure. It does not
mean the model skipped those kernels.

The oversized full-workload raw traces were deleted after coverage validation.
The retained compact pair contains late prefill and short decode samples in one
Prefetto-friendly file per rank:
