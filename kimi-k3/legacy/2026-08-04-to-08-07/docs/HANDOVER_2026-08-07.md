### Runtime attribution and final hybrid policy

The old-ASM BF16 C32 runtime matrix separates the 6087 -> 5684 tok/s gap:

```text
                       Triton 3.6  Triton 3.7
old AITER                  6087.04      5817.34
new AITER                  5945.07      5684.14
```

Triton 3.7 accounts for about `-4.43%`; the newer AITER base adds about
`-2.33%`. The effects are approximately additive.

Paired graph-off/graph-on profiles identify the main buckets:

- Triton 3.7 prefill `extend_attention._fwd_kernel`: `2090 -> 4775 ms`
  for BF16 (2.28x), but only `2949 -> 3295 ms` for FP8 (1.12x).
  This asymmetric BF16 prefill regression is why old ASM FP8 changes from
  negative on Triton 3.6 to positive at C8+ on Triton 3.7; FP8 quant/cache-write
  itself did not get faster.
- Old/new runtime ASM microbench is unchanged within about 1%.
- Fused Q/RoPE/cache-write is also unchanged or slightly slower on Triton 3.7.
- The newer AITER base selects a slower decode MoE stage2 kernel
  (`~3.86 -> 4.22 ms` in the paired profile).
- KDA and MLA ASM were not the source of the newer-base regression.

Persistent symmetry:

- True BF16 persistent C32: `5790.16 tok/s`, versus non-persistent
  `5817.34`; persistent is `-0.47%`, so keeping BF16 non-persistent is correct.
- FP8 non-persistent is unsupported by AITER (`q_type=bf16, kv_type=fp8,
  ps=0` has no heuristic kernel). Persistent FP8 is required.

Final batch-gated policy:

- BF16: padded ASM for batch < 8, native Gluon for batch >= 8.
- FP8: padded ASM for batch < 4, native Gluon for batch >= 4.
- FP8 Gluon uses the device-side runtime split fix described above.

```text

32               5714.25            5930.87     +3.79%
```

The hybrid meets the <=0.5% small-batch regression target and keeps the
high-batch FP8 gain, but still does not beat the production AITER/Triton 3.6
