# Kimi-K3.1 optimization tracker

Owner node: mi355-4. One row per item; update status/result in place after each A/B.
Source analysis: `TRACE_c16_isl8k_20261030.md` (c16 8k/1k trace, 2026-10-30).

## Optimization principles (user, 2026-10-30) — check every op against all five

1. Does this op need to run per layer, or can it move to once per step (layer-invariant metadata)?
2. Is there an unnecessary host sync in the inference flow?
3. Can small kernels be fused to cut launch / ramp cost?
4. Are ops independent? If so, how can they be merged or overlapped (streams, horizontal fusion)?
5. Is each op at its theoretical limit (HBM BW / MFMA peak / link BW)? If not, analyze and propose.

## How every item is measured

1. Baseline and candidate servers differ ONLY in the item's flag/code. Common flags = the
   "T3 trace recipe" in `CONTINUE_HERE.md` (DCP8 + DSPARK, sim acc 3.84, `--disable-radix-cache`).
2. Speed: `scripts/ab_bench.sh <tag>` -> `/shared_nfs/kimi-k31/results/ab/<tag>/summary.txt`
   (decode 8k/1k c4/c16/c48, prefill 8k; fixed seeds, cache flushed per case).
3. Attribution: `scripts/capture_trace.sh <tag> <server_log> 16 8192 1024 5 2`, then
   `scripts/trace_breakdown.py <TP0 trace>`; compare the item's op class ms/step and VERIFY total.
4. Accuracy (any change on a numerics path): gsm8k200 with the real draft (no SIMULATE env),
   score within noise of 0.985 and accept len not collapsing (baseline mean 4.06).
5. Accept only if the endpoint moves; a kernel-only gain is not enough (DEV_RULES).
